Decision · Internal tooling

Build vs. buy, when you already own the data

The quote was about nine thousand dollars a year. What it was selling was a second copy of a record we already had.

Helpdesk agents were asking users questions the helpdesk should already have known the answer to. What laptop is this, is the disk encrypted, when did it last check in. The user usually didn't know, so the ticket went back and forth twice before anyone could start on the actual problem.

The ticketing vendor sells an answer to this. It is an asset management product, it is priced per agent, and for the seats we would have needed it came to roughly nine thousand dollars a year, recurring. That is a list-price estimate for our seat count rather than an invoice we ever received.

I built the thing instead. A sidebar app that authenticates the agent to Microsoft, asks Graph which devices belong to the person who opened the ticket, and renders them next to the conversation. It took about a weekend, plus a few evenings of polish since.

The tell was that the data already existed

Every device fact the agents wanted was already in our device management tenant. It was accurate, and we were already paying for it as part of a licence we held for other reasons. Endpoint management is the system of record for what a laptop is.

So the product wasn't offering to know anything new. It was offering to hold a copy of what Microsoft already knew, in a second place, updated on some sync interval, and to charge per agent for the privilege of looking at it. We would have been paying, per agent per year, for a nicer way to look at data we already had.

That generalises. Buying is usually right when the vendor knows something you don't: they have the integrations, the compliance work, the years of edge cases. Buying is usually wrong when the vendor is charging rent on a join between two systems you already pay for.

What made building defensible

"I could write that" is not a reason to write it. I have inherited enough abandoned internal tools to know that the build column has costs the spreadsheet never shows. Three things made this one hold up.

  • The interface is bounded, and someone else maintains it. This is a read against a documented, versioned, first-party API, so I am not reverse-engineering anything and the surface I depend on does not move without notice.
  • It introduces no new system of record. There is no database and no sync job, so there is no state that can drift out of agreement with reality. The app asks at render time and forgets.
  • The failure mode is the status quo. If the sidebar breaks, the panel is empty and the agent asks the user the question, exactly as before. No ticket is blocked and no data is lost, so I could ship it without a rollback plan. The rollback is ignoring the panel.

Reverse any one of those and I'd have bought. If it needed to store asset history, or if an outage stopped agents working, the maintenance burden and the on-call expectation stop being mine to volunteer for.

The honest cost of building is that the vendor's product comes with a support contract and a roadmap, and mine comes with me. That is a real line item, and it is the one people leave off.

Live data is the wrong thing to put in an audit record

The one piece of state the app does write is a button that drops the current device details into the ticket as an internal note. That looked like a convenience feature and turned out to be the architectural point.

The sidebar reads live. Open a two-year-old ticket and it shows you the machine that person has today. But the question you're asking a closed ticket is what the machine was then: which laptop had the problem, and what its encryption state was when the user reported it.

A live query answers the wrong question about a historical record. So the note is the snapshot, written once, at the moment it mattered, into the place the rest of the ticket's history already lives. The ticket stays readable on its own, by anyone, without the sidebar and without a Microsoft licence.

Where I'd choose differently

The build was right for the question actually being asked, which was "show me a read of data I already own, in the place I'm already working." It scales exactly as far as that sentence does.

If the ask grew into real asset management, meaning procurement, warranty tracking, chain of custody, and write workflows that mutate the record, I would buy, and I would not think about it very hard. Building that would mean owning a system of record, with everything that implies.

With more infrastructure available I'd also change one thing about this version. It queries on every render, so a busy agent generates a lot of identical calls. A short server-side cache in front of the API would fix that, but it needs somewhere to run and something to hold a token, which is exactly the shared infrastructure a one-person build doesn't have. It works fine without it, and it would be tidier with it.
