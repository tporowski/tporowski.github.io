Architecture · Identity

Polling over webhooks, on a host with AD write access

The slower design was the right one, and the reason has nothing to do with performance.

The onboarding automation I maintain has a job that sounds mundane and isn't: it reads incoming HR requests and creates the people. Active Directory identities, Google Workspace accounts, group membership, the downstream tickets that get someone a laptop. To do that it holds write access to the directory.

The obvious design is a webhook. The ticketing system already emits events; stand up an endpoint, receive the request, act on it immediately. Lower latency, less wasted work, and it's the pattern everyone reaches for.

I polled instead. On a schedule, the service asks the ticketing API whether there is anything to do, does it, and goes back to sleep.

What the webhook actually costs

A webhook endpoint is an inbound door. To accept one, this host needs to listen for traffic originating outside itself, and this host can create accounts and modify group membership in the directory. The question stops being "is my handler correct" and becomes "what is the blast radius when it isn't."

Signature verification helps. It doesn't eliminate the class of problem:

  • The listener is reachable, so it can be scanned, fuzzed, and probed by anything that finds it.
  • A signing secret is a credential that lives somewhere, rotates on a schedule someone has to remember, and is only as good as the comparison that checks it.
  • Replay is a real attack against a provisioning system in a way it isn't against a chat notifier. The same message delivered twice means two accounts, or an account restored after it was meant to be gone.
  • Every dependency in the request path (the web server, the framework, the TLS termination) is now attack surface on a domain-privileged machine.

None of that is unmanageable. Plenty of organisations run exactly this safely. But the cost of managing it is ongoing and lands on one person, and the thing it buys is latency I do not need. Nobody has ever needed an account provisioned in four seconds instead of four minutes.

What polling gives up, and what it gives back

Polling inverts the direction of trust. The host makes outbound connections only; nothing is listening. There is no endpoint to discover and no signing secret to rotate. Nothing in the request path needs patching, because there is no request path. The firewall rule is "this machine talks out, nothing talks in," which is a sentence you can hand to a security reviewer without a diagram.

It also authenticates differently. The service runs under a group managed service account: Windows rotates the password itself, on a schedule, and no human ever sees it. There is no credential in a config file for me to accidentally commit, and no shared password that outlives my employment. For the Microsoft side it uses OAuth client credentials scoped to exactly the permissions it needs and no more.

The tradeoff I made: minutes of latency in exchange for a machine with directory write access that accepts no inbound traffic at all.

The part that actually needed care

Polling has one genuine hazard, and it isn't performance. A poll loop will happily do the same work twice. Crash halfway through provisioning, restart, pick up the same ticket, create the account again.

So state lives in the ticket. Each stage of the workflow writes its progress back as a comment, and the automation reads that history before it acts. The ticket is the source of truth about what has already happened, which means the operation is idempotent across restarts: re-running it converges on the same result rather than duplicating it. It also means the audit trail and the state machine are the same artifact. Anyone can open the ticket and read what the system did, in order, without access to a log server.

The second hazard is silence. A webhook failure is loud; a poll loop that has quietly stopped looks exactly like a week with no new hires. That one is solved with a heartbeat: the job reports each cycle, and absence of a report raises an alert. The monitoring had to be built at the same time as the thing it monitors, not after.

Where I'd choose differently

I'm not arguing that polling wins. The argument is that the privilege level of the host belongs in the decision, and usually isn't in it.

If the same integration were read-only (pulling device data into a ticket, say) I'd take the webhook without much thought. If provisioning latency were genuinely user-facing, I'd invert it: keep the privileged worker outbound-only, and put a webhook receiver on a separate unprivileged host that does nothing but drop a message into a queue the worker pulls from. That's the version I'd build with more infrastructure available, and it preserves the property I actually care about, which is that the machine holding directory credentials never accepts a connection from anything.
